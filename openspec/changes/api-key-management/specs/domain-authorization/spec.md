# Spec: Domain Authorization — izg-configuration-console

> **User Story (domain authorization):** *As a sender, I need to be able to validate
> my authority to obtain a credential* — by proving control of a DNS domain — *so that
> I can manage credentials used to send data to IZ Gateway destinations.*
>
> **As-built spec.** This document captures the implemented behavior of domain
> authorization in the API key management feature, plus the planned delta for
> jurisdiction use-type policy. Where behavior is already implemented, scenarios
> describe the code. Where behavior is a planned addition, it represents the agreed
> design in `design.md`.
>
> **Key policy:** For JWT API keys, a DNS domain name is **exclusively bound to one
> sender**. Unlike the mTLS certificate model (where a domain could be shared across
> multiple jurisdictions), a domain may only be authorized for a single sender per
> environment. This is intentional and non-negotiable.
>
> **Conceptual vs physical identity:** the design's conceptual diagram labels the owning
> organization `senderId`; physically that value is the `jurisdictionId` field on the
> single `Jurisdiction` table (`senderId` = `organizationId` = `jurisdictionId`). The
> scenarios below use `jurisdictionId` to match the as-built code.

## ADDED Requirements

### Requirement: Domain ownership is verified before authorization

Before a domain may serve as the basis for a credential, the submitting organization MUST
prove ownership via a DNS TXT record challenge. A domain name is **exclusively
bound** to the first sender that successfully completes domain authorization — it may
NEVER be authorized for a second sender within the same environment. This is a
deliberate departure from the mTLS certificate model, where the same domain could be
shared across multiple senders.

> **Rationale — TXT at the domain apex:** the challenge TXT record is published at the
> apex of the domain being validated (e.g., `kanuri.testing.izgateway.org`), not under a
> `_izg-verify` (or similar) prefix. This intentionally reproduces the DigiCert DNS-TXT
> validation procedure that jurisdiction IT teams already perform for certificate
> issuance, so IIS IT staff need no retraining. Publishing a DNS record is typically a
> multi-day ticketed process for a jurisdiction, so matching the familiar procedure
> avoids added cost and confusion. Domain validation itself is a firm requirement
> (Dave Bike); the apex placement makes meeting it as low-friction as possible.

#### Scenario: Challenge record is issued on first domain submission

- **WHEN** `POST /api/apikeys/verify-domain` is called with a domain that has no
  existing `ApiKeyDomain` record for the given (envId, jurisdictionId) pair
- **THEN** a challenge UUID is generated and stored in `ApiKeyDomain.challengeUuid`
- **AND** `ApiKeyDomain.challengeExpiresAt` is set to 7 days from the request time
- **AND** `ApiKeyDomain.status` is set to `pending_challenge`
- **AND** the response instructs the submitter to place a TXT record at `<domain>`
  (the apex of the domain being validated) with the value `izg-challenge=<uuid>`

#### Scenario: Re-submission reuses an active challenge without generating a new UUID

- **WHEN** `POST /api/apikeys/verify-domain` is called for a domain that already has
  a non-expired `pending_challenge` record for the same (envId, jurisdictionId) pair
- **THEN** the existing `challengeUuid` is returned in the response
- **AND** no new challenge UUID is generated

#### Scenario: DNS verification grants authorization on a successful TXT lookup

- **WHEN** the DNS resolver finds the expected TXT value (`izg-challenge=<uuid>`) as
  a TXT record on `<domain>` (the domain apex, not a subdomain)
- **THEN** `ApiKeyDomain.status` is set to `authorized`
- **AND** `ApiKeyDomain.validatedAt` is set to the current timestamp
- **AND** `ApiKeyDomain.authExpiresAt` is set to 1 year from the current date

#### Scenario: DNS verification fails when TXT record is absent or incorrect

- **WHEN** the DNS resolver does not find the expected TXT value on `<domain>`
- **THEN** `ApiKeyDomain.status` remains `pending_challenge`
- **AND** the response indicates verification failure with a diagnostic message

### Requirement: Domain authorization is scoped to a single environment by default, with cross-environment credentials available for admin and operational staff

For standard credentials, an `ApiKeyDomain` authorization MUST be honored only for the
(envId, jurisdictionId) pair under which it was created. A sender authorized in
environment 5 cannot use that authorization in environment 6.

For credentials issued to staff with administrative or operational roles (IZG Operations
or Jurisdiction Operations), a single domain authorization MAY be used to issue a
credential valid across multiple environments. This supports support engineers and
administrators who need consistent access across development, test, staging, onboarding,
and production without maintaining separate credentials for each. This cross-environment
privilege is role-gated and is NOT available for standard sender credentials.

#### Scenario: Standard credential is restricted to its authorization environment

- **WHEN** an `ApiKeyCredential` is created for a normal (non-admin) sender
- **THEN** the credential is valid only in the environment in which the domain was
  authorized
- **AND** the Hub MUST reject the credential if presented in any other environment

#### Scenario: Admin or operational credential may span multiple environments

- **WHEN** an `ApiKeyCredential` is created for a user with IZG Operations or
  Jurisdiction Operations role
- **THEN** the credential MAY be scoped to a list of environments rather than a
  single environment
- **AND** the Hub MUST accept the credential in any environment in its authorized set

#### Scenario: Domain authorized for one jurisdiction is not returned for another

- **WHEN** `GET /api/apikeys/domains` is called with envId=5 and jurisdictionId=2
- **THEN** only domains whose `ApiKeyDomain` record has `jurisdictionId = "2"` and
  `env = "5"` and `status = "authorized"` and `authExpiresAt` in the future are returned

#### Scenario: Domain authorized in environment A is not listed for environment B

- **WHEN** `GET /api/apikeys/domains` is called with envId=6 and jurisdictionId=2
- **THEN** a domain authorized only under envId=5 for the same jurisdiction is NOT returned

### Requirement: Domain authorization expires after one year

An `ApiKeyDomain` authorization MUST expire exactly 1 year from the date of
DNS verification. After expiry, the domain remains visible in the domain list so
the organization can re-initiate the DNS challenge, but it MUST NOT be selectable
as an already-authorized domain when creating a new credential.

#### Scenario: Expired domain is still returned by the domain list

- **WHEN** `GET /api/apikeys/domains` is called
- **THEN** domains with a past `authExpiresAt` are included in the response
- **AND** their expired status is communicated so the UI can indicate re-authorization is required

#### Scenario: Expired domain cannot be used as an existing authorized domain for credential creation

- **WHEN** `POST /api/apikeys` is called with `dnsChoice === 'existing'` and the
  selected domain's `authExpiresAt` is in the past
- **THEN** the request MUST be rejected with an appropriate error indicating the
  domain authorization has expired and must be renewed via DNS challenge

### Requirement: DNS verification bypass MUST NOT be reachable in production

The development-only bypass in `POST /api/apikeys/verify-domain` MUST NOT be reachable in
production. It currently activates automatically when `NODE_ENV === 'development'`; it MUST
be refactored to require an explicit opt-in flag, and MUST be blocked unconditionally when
`NODE_ENV === 'production'` even if the flag is set.

> **Source:** Palak Patel, `api-key-management-ui` CR, IGDD-2707.
> **Code change required:** `verify-domain/index.ts` currently uses
> `if (process.env.NODE_ENV === 'development')` with no explicit flag — this must
> be hardened per the scenarios below.

#### Scenario: Real DNS lookup is performed by default regardless of NODE_ENV

- **WHEN** `POST /api/apikeys/verify-domain` is called without the bypass flag enabled
- **THEN** a real DNS TXT record lookup is performed on `<domain>`
- **AND** `NODE_ENV` alone does NOT enable bypass behavior

#### Scenario: Bypass is permitted only outside production with explicit opt-in

- **WHEN** the bypass flag is enabled AND `NODE_ENV !== 'production'`
- **THEN** the endpoint MAY skip the real DNS lookup and simulate a successful verification

#### Scenario: Bypass MUST be ignored in production even when explicitly enabled

- **WHEN** the bypass flag is enabled AND `NODE_ENV === 'production'`
- **THEN** the bypass flag MUST be ignored
- **AND** a real DNS TXT record lookup MUST be performed on `<domain>`
