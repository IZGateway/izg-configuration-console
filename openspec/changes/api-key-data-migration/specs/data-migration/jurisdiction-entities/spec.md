## Purpose

Specifies the required outcome of populating and backfilling Jurisdiction entity records
in DynamoDB so that each Jurisdiction currently receiving messages via IZ Gateway has
accurate `allowedUseTypes` and routing metadata in place before the JWT API Token
feature is enabled.

## Input Data

The `allowedUseTypes` values for this migration are sourced from the authoritative
Salesforce report:

**`# of IIS's Participating in any Use Case-2026-08-13-20-12-21.xlsx`**

The derived mapping is captured in:

**`openspec/changes/api-key-data-migration/jurisdiction-allowed-use-types.csv`**

The report provides boolean flags per jurisdiction:
- `IIS to IIS Data Exchange = true` → `PUBLIC_HEALTH`
- `Provider to IIS Data Exchange = true` → `PROVIDER`
- `Consumer Access Data Exchange = true` → `PATIENT`

**Manual overrides (Salesforce not yet updated):**
- **District of Columbia** — report shows no Consumer access; `PATIENT` retained per
  confirmation from Michelle C.
- **South Carolina** — report shows no use types; `PROVIDER` confirmed manually by ops.
- **Hawaii** — not yet onboarded; no `allowedUseTypes` written; migration skips this record.

**Sub-state entries to skip:** Some jurisdictions tracked in Salesforce at the city or
county level use their parent state's IIS infrastructure and SHALL NOT receive their own
Jurisdiction records. The following entries are flagged `SKIP` in the CSV:
- Chicago - Illinois (uses Illinois state IIS)
- Houston - Texas (uses Texas state IIS)
- San Antonio - Texas (uses Texas state IIS)
- LA County - California (uses California state IIS)
- Maricopa County - Arizona (uses Arizona state IIS)

**Exceptions — these sub-state entries DO have their own IZ Gateway connections and
SHALL receive records:** New York City - New York State, Pennsylvania - Philadelphia.

**Test entries excluded:** `Test IIS 1` and `Test IIS 2` are not real jurisdictions
and SHALL NOT be written to DynamoDB.

**CDC/DEX excluded from Jurisdiction records:** The `dex` endpoint (CDC data reporting)
is not an IIS jurisdiction and SHALL NOT receive a Jurisdiction entity record in this
migration. AllowedUser records referencing `dex` as a destination are generated by the
access-control migration, not this one.

**DEVELOPMENT and CCUAT jurisdiction records:** These logical jurisdictions exist in
`prod_config.json` and `onboarding_config.json` but do not appear in Salesforce.
They represent test and connectivity-testing endpoints accessible by any sender type.
The migration SHALL write Jurisdiction records for DEVELOPMENT and CCUAT with
`allowedUseTypes: [PUBLIC_HEALTH, PROVIDER, PATIENT]`, sourced from the config files.

**Docket relationship:** Any Jurisdiction with `PATIENT` in its `allowedUseTypes`
is accessible by the Docket sender (whose `useTypes` is `PATIENT` only). The
`allowedUseTypes` value drives this implicitly — no additional configuration is needed.

## ADDED Requirements

### Requirement: All active Jurisdictions have allowedUseTypes populated

Every Jurisdiction entity that currently receives messages via IZ Gateway SHALL have
its `allowedUseTypes` attribute set to reflect the use cases that Jurisdiction has
adopted, as determined by the input data collected from Salesforce.

A Jurisdiction with no `allowedUseTypes` value would deny all API-key traffic at the
Hub's use-type intersection check; this is a blocking precondition for enabling the
feature.

#### Scenario: Jurisdiction present in input data

- **WHEN** the migration runs and the input data contains an entry for a Jurisdiction
- **THEN** that Jurisdiction's record in DynamoDB SHALL have `allowedUseTypes` set to
  the values from the input data

#### Scenario: Jurisdiction record update fails

- **WHEN** the migration runs and a `update-item` call for a Jurisdiction fails
  (e.g. due to a permissions error or transient DynamoDB failure)
- **THEN** that failure SHALL be logged to stderr with a `FAILED:` prefix identifying
  the Jurisdiction ID
- **AND** the migration SHALL continue processing remaining records

**Note:** DynamoDB `update-item` will create a new item if the target key does not
exist, so a missing Jurisdiction record will not produce a failure — it will be
silently created with only the attributes set by the migration. This is a known
limitation: the migration does not detect or report pre-existing missing records.

### Requirement: Migration is idempotent

The migration script SHALL be safe to run more than once against the same database
without producing duplicate records or corrupting existing data.

#### Scenario: Re-run against already-migrated database

- **WHEN** the migration is run a second time with the same input data
- **THEN** the resulting DynamoDB state SHALL be identical to the state after the first run
- **AND** no records SHALL be duplicated or incorrectly overwritten

### Requirement: Existing Jurisdiction records are not removed

The migration SHALL NOT delete any existing Jurisdiction records from DynamoDB,
regardless of whether they appear in the input data.

#### Scenario: Jurisdiction absent from input data but present in DynamoDB

- **WHEN** a Jurisdiction exists in DynamoDB but is not in the migration input data
- **THEN** that record SHALL remain unchanged in DynamoDB after the migration completes

### Requirement: Migration produces an execution report

Upon completion the migration SHALL emit a summary report that identifies:
- the number of Jurisdiction records updated
- any records that could not be updated, and the reason

#### Scenario: Successful run

- **WHEN** the migration completes
- **THEN** the report SHALL list the count of records updated and any failures
- **AND** the exit status SHALL indicate success if no write errors occurred
