## Why

Operations staff need an audit trail: when reviewing logs, they must be able to tell **which authenticated user initiated the action** that produced each log message. Today the Configuration Console attaches user identity to only a handful of log lines (the `API Request` middleware line, the Elasticsearch query handler, and some access-group/denylist handlers). The vast majority of log events (page navigations, database warnings, connection tests, errors) carry no identity at all, so an action cannot be reliably traced back to a user or login session. (IGDD-2223)

## What Changes

- Add a Winston log format that automatically injects a new **`sessionUser`** identity object into **every** Node-runtime log event when a request context is present — no per-call-site changes required. This is the Node analog of the Hub's SLF4J MDC + `LogstashEncoder` approach.
- **Additive and non-breaking.** `sessionUser` is a brand-new field. This change does **not** modify or remove any field that is logged today — notably the existing `user` (string) and `sub` fields used across many handlers stay exactly as they are. This preserves existing Elastic/Kibana queries and avoids an index mapping conflict on the established `user` field.
- `sessionUser` shape (camelCase):
  ```json
  "sessionUser": { "name": "...", "userId": "...", "email": "...", "sessionId": "...", "jti": "...", "authTime": 0, "ip": "..." }
  ```
- Introduce a **`sessionId`** generated by CC at sign-in (`crypto.randomUUID()`), persisted on the next-auth token — stable for the life of a login session, not a secret, non-replayable. The Okta ID-token **`jti`** is logged alongside it (as `sessionUser.jti`) as a token reference. Both are present.
- Support **indirect correlation to the Okta System Log** via `userId` (Okta `sub`) + `authTime` (Okta login timestamp) + `ip` — all carried inside `sessionUser`. The direct-pivot option (Okta `sid`, which requires enabling Front-Channel SLO) is **not** being pursued now; it remains a documented future option (a drop-in source change for `sessionId`).
- Add a **per-session authorization snapshot**: a single `Session established` record logged **once per login** (in the `jwt` callback) containing the `sessionUser` identity plus the user's **`groups`** and resolved **`role`**. This captures point-in-time authorization (Okta membership is mutable) without repeating the group list on every line.
- **Leave the Edge `Route Request` log unchanged** (it stays anonymous, as today). Page-level data access is attributed via the structured `/api/*` logs; structured page-view attribution in Edge middleware is a possible follow-up.

## Capabilities

### New Capabilities
- `audit-log-user-identity`: Every log message generated during an authenticated user interaction carries a `sessionUser` identity object (name, userId, email, sessionId, jti, authTime, ip), added without disturbing existing log fields, enabling logs to be traced back to the initiating user and login session. Covers how identity is sourced (Okta token claims + a CC-generated session id), how it is injected (request-context-aware Winston format), the once-per-session authorization snapshot, and behavior for unauthenticated / no-context events.

## Impact

- **Code:**
  - `logger.ts` — new request-context-aware format that injects `sessionUser`.
  - `src/lib/Context.ts` — extend `Context` with `userId`, `email`, `sessionId`, `jti`, `authTime` (`ipAddress` already exists).
  - `src/pages/api/api-middleware-helper.ts` — populate the new context fields in `withMiddleware`. The existing `logApiRequest` line (and its `user`/`sub`) is left **unchanged**.
  - `src/pages/api/auth/[...nextauth].ts` — in the `jwt` callback: generate `sessionId`, capture `authTime` + `jti` from the decoded ID token, persist on the token, and emit the once-per-login `Session established` record (with `groups` + resolved `role`).
  - `src/next-auth.d.ts` — type augmentation for `sessionId`, `authTime`, `jti` on the JWT.
  - **Not changed:** `src/middleware.ts` (Edge `Route Request` stays as-is) and `src/pages/api/elasticsearch/query.ts` (its existing `user` field is preserved).
- **Backward compatibility:** Additive only. No existing logged field's name, type, or presence changes → no breaking changes to existing Kibana queries/views or Elasticsearch mappings.
- **Auth / security:** Reads additional Okta ID-token claims (`auth_time`, `jti`) and generates an opaque `sessionId`; no change to authentication, authorization, jurisdiction scoping, or encrypted fields. No raw JWT, access token, ID token, or session cookie value is ever logged. The per-session `groups`/`role` snapshot is a point-in-time authorization record — logs should be access-controlled accordingly.
- **Scope:** Configuration Console only. The Hub (`izgw-core`/`izgw-hub`) implements the equivalent via its own CR; Transformation Console is tracked separately.
- **Logging pipeline / observability:** New `sessionUser.*` fields appear on Node-runtime log documents shipped to Elasticsearch; Kibana mappings auto-discover them on first event. Edge `Route Request` lines are unchanged. No log-config (nginx/filebeat) changes required.
